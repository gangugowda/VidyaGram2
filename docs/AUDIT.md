# Repository audit

Audit of the VidyaGram repository as it was handed over, followed by what this
change set did about it.

- Baseline commit: `4ab4379 chore: baseline import of VidyaGram demo (frontend-only)`
- Audit scope: repository structure, build/tooling, data handling, security and
  honesty of the UI claims.

---

## 1. What the original repository was

A single Vite + React + TypeScript application (51 source files) that ran
entirely in the browser:

- The whole "school" (users, classes, attendance, marks, quizzes, feedback,
  audit log) was generated by `src/lib/seed/` and written to `localStorage`
  under `vidyagram.db.v4`.
- "Sign-in" compared a SHA-256 hash of the password with a hash stored in that
  same `localStorage` blob.
- Every role could read every record; access control was a set of client-side
  helper functions in `src/lib/access.ts`.
- There was no server, no database and no test suite.

As a **reviewable product demo** this was genuinely good: the role dashboards,
the six-language interface, the privacy copy and the "integrations are not
configured" labelling were all honest and complete.

As a **codebase to build an MVP on**, it had structural and security problems.

## 2. Findings

| # | Area | Finding | Severity | Resolution |
| --- | --- | --- | --- | --- |
| 1 | Structure | One flat `src/` for a 51-file app; no separation between UI, domain rules and data. Nothing could be reused by a server. | High | Converted to npm workspaces: `apps/web`, `apps/api`, `packages/shared`. |
| 2 | Security | Passwords were SHA-256 over `salt::password` and the hashes shipped to every browser. Any visitor could read every account hash. | Critical | Passwords now use scrypt (`node:crypto`) and never leave the server. The API never serialises `passwordHash`/`salt`. |
| 3 | Security | Authentication was a `localStorage` user id. Anyone could set it and become any role, including admin. | Critical | Opaque, DB-backed session tokens in an `httpOnly`, `SameSite=Lax` cookie; sessions are revocable and expire. |
| 4 | Security | No authorisation boundary: all data for the school was in the client bundle. | Critical | Role-scoped read model built on the server (`apps/api/src/lib/bootstrap.ts`); students/guardians receive only their own private rows. |
| 5 | Data | All state was per-browser. Two devices, two different schools; no shared record, no audit trail with any integrity. | High | SQLite persistence with a metadata-driven schema and migrations; server-side audit log. |
| 6 | Integrity | Quiz answers and explanations were in the client payload, so "grading" was advisory. | High | Server-side grading; answer keys are stripped from the payload while results are withheld. |
| 7 | Correctness | `localStorage` writes could silently fail (quota) and the UI still reported success. | Medium | Demo writes now surface a storage error toast; server writes surface API failures. |
| 8 | Correctness | No tests at all. | High | 15 API integration tests (`apps/api/test/api.test.ts`) covering auth, scoping, grading, guardian approval and admin safety. |
| 9 | Tooling | No CI, no shared typecheck, no single `npm run build`. | Medium | Root scripts (`dev`, `build`, `typecheck`, `test`) plus a GitHub Actions workflow. |
| 10 | Type drift | Domain types were duplicated between the browser app and the sample data. | Medium | `packages/shared` owns the domain model, pure helpers, seed data and wire contracts. |
| 11 | Docs | `README.md` described a frontend-only app; there was no architecture or API reference. | Medium | `README.md` rewritten; `docs/AUDIT.md`, `ARCHITECTURE.md`, `API.md`, `ROADMAP.md` added. |

## 3. Things that were deliberately kept

The demo's product work is the valuable part, so it was preserved:

- The full UI: dashboards, class/attendance/marks/quiz/lab/library screens,
  admin screens, sign-up flow and the design system.
- The six-language interface with published coverage percentages and English
  fallback.
- The privacy gates in `apps/web/src/lib/access.ts` and the route guards.
- The coherent sample dataset, now in `packages/shared/src/seed` and reused by
  both the browser demo and the API seeder.
- The honesty rules: no success message for an unconfigured integration, no
  claim that a local action reached a server.

## 4. What changed in this commit

- Monorepo conversion (`apps/web`, `apps/api`, `packages/shared`).
- New Fastify 5 + SQLite API with:
  - scrypt password hashing and cookie sessions,
  - role-based authorisation on every route,
  - role-scoped bootstrap snapshots,
  - server-side quiz grading and marks publishing,
  - guardian-link approval workflow,
  - audit trail, notifications and rate limiting.
- A browser API client (`apps/web/src/lib/api.ts`) and store integration for
  sign-in, sign-up, sign-out, bootstrap and server-graded quiz attempts, with a
  documented fallback to the on-device demo dataset.
- A visible data-mode notice on the sign-in, sign-up and in-app screens stating
  where the data actually lives.
- API integration tests, CI workflow and documentation.

## 5. Known gaps after this change

These are real and are tracked in [ROADMAP.md](ROADMAP.md):

- Only sign-in, bootstrap reads and quiz grading are wired to the API from the
  UI. Other edits (attendance, marks entry, announcements, doubts, feedback,
  parent links, admin actions) still mutate the local snapshot in server mode.
  The UI states this explicitly rather than claiming a save.
- No password reset, e-mail verification, MFA or account lockout policy.
- SQLite is appropriate for a pilot, not for a multi-school district rollout.
- No automated accessibility or visual-regression tests.
